# 现状盘点与实测基线（V1.2.0 开工前）

> 日期：2026-11-05 · 机器：Mac17,8 / Apple M5 Pro / 64 GB / macOS 27.0.1 / Python 3.9.6
> 本文件只记录**实测数字与代码事实**，不作估算。所有测试数据均为脚本生成的虚构消息。

## 一、多群聊支持现状

| 层 | 现状 | 缺什么 |
|---|---|---|
| 数据层 | `chat_info(chat_id UNIQUE)` + `messages.chat_id` + `message_key=chat_id:message_id`，同一 `.db` 可存多个群；去重键天然按群隔离 | 群表无重命名/显示名字段；`import_log` 没有 `chat_id`；统计接口只有全库维度；`get_chat_info()` 无参时只返回第一行 |
| 导入 | 一个 JSON 对应一个群；同一数据库可连续导入多个群；二次导入按 `chat_id:message_id` 去重 | 无“导入到指定群”之外的群管理；导入记录无法按群归属 |
| GUI | 只有单库、全库统计、全库导入历史；标题栏只显示第一个群 | 无群列表、切换、重命名、删除、每群统计 |
| 聊天查看器 | `chat_viewer/app.js` 通过 `fetch('chat_data.json')` 读取**单个群的 JSON**，无群概念 | 不能切换群，不能从统一库读取 |
| 热力图 | `data_processor.py` 每次处理**单个 `result.json`** | 不能按群切换，不能从统一库生成 |

**结论**：数据层“能存多群”，产品层“看不到多群”。V1.2.0 需要补：统一库群列表、切换、重命名、受控删除、每群统计与导入记录。

## 二、20 万条消息实测（真实运行，不外推）

测试数据：`scripts/generate_demo_data.py --messages 200000 --days 730`，实际生成 **232,707 条**虚构消息，JSON 103 MB。

### 2.1 导入（v1.1 代码，CLI）

```
/usr/bin/time -l python3 sql_converter/json_to_sqlite.py --json result.json --db base.db
```

| 指标 | 实测值 |
|---|---|
| 导入耗时 | **4.04 s**（real） |
| 内存峰值（maximum resident set size） | **1,294,450,688 B ≈ 1.21 GiB** |
| 新增消息 | 232,707 |
| 数据库大小 | 181 MB |
| 完整性校验 | 通过（重复键 0、孤儿实体 0） |

问题定位：一次性 `json.load` 载入 103 MB JSON + 实体/哈希对象，导致内存峰值 ≈ 1.2 GiB；随消息量线性增长，不可接受。

### 2.2 聊天查看器（v1.1 代码，Chrome headless 1440×900）

| 指标 | 实测值 |
|---|---|
| 首屏渲染 | **372.6 ms** |
| 滚动平均帧率 | **60.1 FPS** |
| P95 帧率 / 帧耗时 | **59.5 FPS / 16.8 ms** |
| JS 堆占用 | **197.0 MB** |
| 虚拟滚动实际节点 | 14–22 个 |
| 3 秒滚动距离 | 108,600 px |

结论：这台 M5 Pro 上滚动本身不卡，但**整份 103 MB JSON 全量载入内存**（JS 堆 197 MB），不满足“避免全量载入内存”。

### 2.3 分页查询（SQLite v2 索引）

| 查询 | 实测 |
|---|---|
| `COUNT(*) WHERE chat_id=?` | 4.9 ms |
| `ORDER BY date_unixtime LIMIT 500 OFFSET 100000` | **82.7 ms** |
| `COUNT(DISTINCT sender_id) WHERE chat_id=?` | 37.7 ms |

结论：缺少 `(chat_id, date_unixtime)` 复合索引，深分页 82.7 ms 偏高；V1.2.0 需加复合索引并改为 keyset/row_id 分页。

## 三、UI 判断

当前真实界面截图：`docs/screenshots/gui_import.png`（Tkinter）、`docs/screenshots/chat-viewer-virtual.png`、`docs/screenshots/heatmap-timeline.png`。

| 界面 | 判断 | 理由 |
|---|---|---|
| Tkinter 导入器 | **丑，重做** | clam 主题 + 1px 灰色描边，控件像 2010 年的 Windows 表单；标题栏是系统默认样式，在 macOS 上不协调；emoji 当图标；统计卡片两列平铺，没有视觉层级；无法实现真实毛玻璃 |
| 聊天查看器 | 小改 | 深色 Telegram 风格基本成立，但字体、间距、工具栏与整体品牌不一致 |
| 热力图 | 小改 | 图表可读，但页面边框、间距、标题层级偏旧 |

**结论**：GUI 外壳与主导航全部重做（原生 macOS 毛玻璃窗口 + Web 视图），图表与查看器的渲染逻辑保留并统一视觉规范。

## 四、V1.2.0 技术选型

- **GUI 外壳**：PyObjC（AppKit + WebKit），窗口内容视图为 `NSVisualEffectView`（`behindWindow` 混合），`WKWebView` 背景透明——这是 macOS 真实系统模糊，不是 CSS 假玻璃。
- **界面层**：HTML/CSS/JS + 本地 HTTP API；图表沿用 ECharts 本地 vendor。
- **打包**：PyInstaller `--windowed` 生成 arm64 `.app`。
- 理由：Tkinter 无法提供系统 vibrancy；Electron/Tauri 体积与构建链过重；PyObjC + WKWebView 体积小、系统原生、可直接读取现有 Python 数据层。
