## 3. 已具备能力

- JSON → SQLite：消息、文本实体、回复、转发、媒体类型、原始 JSON。
- GUI 导入：文件选择、预览、后台线程、进度条、统计、导入历史。
- 去重：GUI 路径按 `messages.id` 过滤已存在消息。
- 热力图：7×24 活跃度、每日趋势、关键词、时段、用户排行。
- 聊天查看器：Telegram 风格、搜索、用户筛选、回复跳转、深色模式。
- 截图：`docs/screenshots/` 已有 5 张（GUI 三张 + 热力图 + 聊天查看器）。
- 示例数据：仅 8 条合成消息，不足以演示大数据量。

## 4. 与本轮目标的差距

| 目标 | 现状 | 问题 |
|------|------|------|
| 增量导入 / 可验证去重键 | 按单列 `messages.id` 去重 | Telegram 消息 ID 是“群内序号”，多群合并时主键冲突；`messages.id` 同时是主键，无法容纳两个群相同 ID |
| 重复导入不产生重复数据 | GUI 路径基本可用 | CLI 使用 `INSERT OR REPLACE`，且每次重复插入 `text_entities`，二次导入会产生重复实体 |
| CSV / Parquet 导出 | 无 | 只能查库，无法交付给 Excel / 数据分析工具 |
| 可交互时间轴 | 每日柱状图可点击某一天 | 不能缩放时间窗口，也不能按日期区间联动筛选统计/关键词/时段 |
| 大数据量分页 + 虚拟滚动 | 每帧追加 50 条，最终把所有消息塞进 DOM | 几万条后 DOM 节点过多；`getReplyText` 用 `find` 全表扫描，回复渲染 O(n²) |
| 仓库门面 | License 有，Topics 无，Description 偏长 | 缺 Topics，首屏截图与本轮新 UI 不一致 |
| 中文文档 | README + 零散开发文档 | 缺 RequirementsSpec / SystemDesign / APISpec / TestPlan / CHANGELOG |

## 5. 风险与约束

- 数据库 schema 需要升级到 v2（`message_key = chat_id:message_id` 唯一键），必须兼容已有 v1 数据库并自动迁移。
- Parquet 导出依赖 `pyarrow`，需要作为可选依赖并在缺失时给出明确提示。
- 截图只能使用合成数据；真实聊天 JSON、DB 均被 `.gitignore` 排除。
- 本轮只改本仓库，不触碰其他仓库；不 force push、不删库。
